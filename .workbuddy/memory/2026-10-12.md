# 2026-10-12

## 调查：Auro 的后台形态、部署可行性、单机一体化、Squad 路由（纯代码/文档核查，未改文件）

背景：纯均连续追问「用户登录网站 + daemon CLI 就能完整执行项目吗」「你没有后台 worker 么」「vercel+supabase+redis 能部署吗」「能不能把 Go 单体也装本机、包装成统一服务」「团队的路由是什么」。

### 一、Auro 的「后台」形态（无独立 job worker 进程，无消息队列）

1. **真执行 worker = `auro daemon`**，跑在用户机器上，经 WebSocket 长连接挂到 server（`server/internal/daemonws/{hub,notifier,rpc_dispatch,pending_work}.go`）。server 靠这条连接下派任务，daemon spawn 本机 agent CLI。
2. **server 进程内 DB-backed scheduler**（`server/internal/scheduler/`，MUL-2957）：`sys_cron_executions` 表当分布式锁 + 审计，多副本同时 tick 只有唯一键赢家；任务含 `jobs_autopilot` / `jobs_issue_wakeup` / `jobs_plugin_hook` / `jobs_search_index` / `jobs_task_usage` / `jobs_child_done`。
3. **server 进程内 sweeper**：`cmd/server/runtime_sweeper.go`、`source_context_sweeper.go`。
4. **独立二进制**：`cmd/maintenance`（`MAINTENANCE_PORT`）、`cmd/migrate`、6 个 `cmd/backfill_*`。

关键判据：**scheduler 必须常驻进程**，这一点决定 serverless 不可行。

### 二、Vercel + Supabase + Redis 可行性

- **Vercel 放 Go 后端：不行**。硬阻塞三处：常驻 scheduler（每 30s tick）、daemon 的常驻 WS hub、启动时跑 1000+ SQL 迁移。Vercel 原生 WS（2026-06 public beta）连接绑定单 Function 实例，默认 5 分钟断开（Pro 800s / beta 1800s），且状态不能留内存 —— 支撑不了 daemon 长连接。仓库内**零 Vercel 配置**（16 处 vercel 命中全是 landing 页竞品文案等无关内容）。
- **Supabase 当 Postgres：可以，但有降级**。扩展依赖：`pgcrypto`（001_init 必需）、`pg_trgm`（137）、`pg_bigm`（032/446/447，**Supabase 白名单没有** → 已用 `DO $$ ... EXCEPTION` 包住，只丢 CJK bigram 索引，不中断迁移）、`pg_cron`（076，同样 EXCEPTION 包住，可缺）。
- **Supabase 连接方式约束**：全仓无 `PreferSimpleProtocol` / `default_query_exec_mode` / pgbouncer 兼容配置 → pgx 默认扩展协议 + 用了 advisory lock（rollup 4246）→ **必须直连 5432 或 session 模式，不能用 6543 transaction pooler**。
- **Redis：本来就可选**。`REDIS_URL` 空 = in-memory hub 单节点模式；缺失只损失 auth 限流（router.go:1501 WARN）、跨副本 realtime relay、企微 channel lease、token/claim 缓存。

### 三、单机一体化：Go 后端装本机 + 包装成「一个统一服务」

核查事实：
- **daemon 是 detached 后台进程**：`server/cmd/auro/cmd_daemon_unix.go` 用 `SysProcAttr{Setsid: true}` spawn（Windows 走 CREATE_BREAKAWAY_FROM_JOB），CLI 只是 supervisor；daemon 有自己的 PID 文件、daemon.log 轮转、`/health` 端口、`daemon status/logs` 子命令。
- **CLI 与 server 同一个 Go module**：`cmd/auro` 与 `cmd/server` 只是两个 main，daemon 逻辑在 `internal/daemon`，共享全部 internal 包 → 合并成单进程技术上没有障碍，只是要不要的问题。
- **Desktop 已经是官方「统一客户端」**：`apps/desktop/scripts/bundle-cli.mjs` 从 `server/cmd/auro` 编译 CLI 塞进 `resources/bin/`；`src/main/cli-bootstrap.ts` 有 `ensureManagedCli`（缺失时从 GitHub Releases 拉 + sha256 校验自修复）；`src/main/daemon-manager.ts` 用 `execFile` 驱动 `auro daemon start`，轮询 /health + PID + 日志 tail，另有 `daemon-recovery.ts` / `daemon-auth-probe.ts`。**Desktop 不含 server**，它连远端。
- **无嵌入式数据库路径**：全仓 `embedded-postgres` / `litestream` 命中 0；`sqlite` 的 18 处命中是 skills 包格式，与 DB 无关。

结论：装本机可以（`install.sh --with-server` / `make selfhost` 官方路径），但必须带 PostgreSQL。「统一服务」按粒度分三层 —— 编排层（launchd/systemd 一个单元拉起 compose + daemon）推荐且今天可做；进程层（server + daemon 合一个进程）可行但生命周期与崩溃域耦合，不建议；数据层（去掉 Postgres）不可行。

### 四、可行组合（若要上线）

前端 `apps/web` → Vercel；后端 Go → 常驻容器（Fly/Railway/Render/VPS）；DB → Supabase PG17（直连）；Redis → Upstash（可选）；daemon → 用户机器。注意 `apps/web/proxy.ts` matcher 含 `/ws`、`/v1`，Vercel rewrite 不代理 WS 升级 → 浏览器需直连后端域（`NEXT_PUBLIC_API_URL`/`NEXT_PUBLIC_WS_URL`）+ 同站 cookie（`COOKIE_DOMAIN`）。

### 五、Squad（团队）路由：全部收敛到 leader_id

权威来源 `server/internal/service/builtin_skills/auro-platform/references/squads.md`（内置 skill，是给 agent 读的行为契约，比 docs 更硬）。

不变量：**squad 是「路由与协调对象」，不是 agent，自己不执行任何工作；所有 squad 路由都收敛到 `squad.leader_id`。**
- 指派 issue 给 squad（`assignee_type="squad"`）→ 路由到 leader，不扇出给成员
- `[@Name](mention://squad/<id>)` → 解析 squad、读 leader_id、入队 leader 任务
- squad autopilot → 可执行 agent = leader（`create_issue` 型保留 squad 作为 assignee，`run_only` 型直接给 leader 建任务）
- 成员是花名册：`role` 只是 briefing 里的标签，无调度/权限语义；`instructions` 是 leader briefing 内容，不注入成员；`description` 无运行时影响
- leader briefing = Squad Operating Protocol + Roster（含 agent 成员的 skills 列表，便于按能力委派）+ instructions（非空时）
- backlog 中的指派不立即开工；移出 backlog 才触发 leader；改 assignee 先取消该 issue 现有任务
- 父 issue 状态由 leader 管：首次派发应置 `in_progress`，确认整体目标达成才 `in_review`；**server 不会因 child 完成而自动翻父状态**
- 状态权限仅在 issue 的 assignee 指向该 squad 时授予；被 @ 进别人的 issue 时 briefing 会携带「不要改这个 issue 的状态」
- 创建必须给 `leader_id`（须属本 workspace 的 agent），leader 自动成为 `role=leader` 成员；archived squad/leader 在路由与派发处 fail-closed
- leader 决策记录：`auro squad activity <issue-id> action|no_action|failed --reason "..."`（必须针对本 turn 正在跑的 issue；stage barrier 唤醒时跑在 PARENT 上）
- worker 的回复会唤醒 assigned leader，无需显式提及；leader 当轮已在跑则顺延到下一轮
- 前端页面路由：`apps/web/app/[workspaceSlug]/(dashboard)/squads` 与 `.../squads/[id]`
- 相邻机制：migration `128_comment_routing_escalation` 给 `agent_task_queue` 加了 `escalation_for_task_id` / `fire_at` / `deferred` 状态
- 侧效清单（会触发 agent 或改状态）：建 squad、改字段、换 leader、增删成员、改 role、指派、移出 backlog、在 squad 指派 issue 上评论、提及 squad、squad autopilot、`squad activity`、删除/归档
