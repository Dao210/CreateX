# 本机使用性能分析（2026-10-24）

实施结果见 [2026-10-25 优化验收](local-performance-optimization-2026-10-25.md)。

用户反馈：日常使用过程中响应慢。本次检查当前源码、运行进程、Next 开发 trace、浏览器日志及已有生产构建；未修改应用代码或运行配置。

## 结论

本次证据最支持优先优化前端加载及公共页面壳的开销：日常使用仍运行 Webpack 开发服务，访问页面会触发编译；公共布局静态依赖大量业务组件；关闭的浮动聊天仍挂载查询和内容。聊天事件的重复刷新，以及逐次输入同步保存草稿，也是明确值得优化的代码路径。

当前没有证据把数据库或 Go 后端列为第一瓶颈。输入、滚动和游戏帧率尚无有效浏览器性能基线，不能把下述代码开销直接等同于已测得的交互延迟。

## 建议顺序

### P0：给日常使用提供生产运行模式，缩减开发启动链

- 当前 `apps/web/package.json:7` 的 dev 命令明确使用 Webpack；根 `dev:web` 再通过 Turbo 启动它。日常操作会承担首次访问路由编译和开发资源加载成本。
- 为托管环境脚本增加明确的开发/生产运行模式。日常使用走已构建的 `next start`；修改前端时使用开发模式。生产构建应可识别源码是否已变化，避免误用旧产物。
- 单个 Web 开发任务可直接调用 `pnpm --filter @auro/web dev`，并验证是否消除当前 Turbo 子进程的持续 CPU 占用。多包构建、检查仍可保留 Turbo。
- 验收：相同机器、相同路由分别记录首次进入、重复导航、CPU、RSS；不要只比较启动 Ready 时间。

依据：[Next.js 本地开发说明](https://nextjs.org/docs/app/guides/local-development)明确区分按访问编译的开发服务与预构建生产服务。

### P0：拆分公共布局中的重组件

相关位置：`packages/views/layout/dashboard-layout.tsx:5`、`packages/views/modals/registry.tsx:5`、`apps/web/app/[workspaceSlug]/(dashboard)/layout.tsx:5`。

- ModalRegistry 虽然按当前 modal 渲染一个弹窗，但它静态导入了所有弹窗；新建事项又静态导入人工与 Agent 两套面板及其编辑器依赖。
- 公共页面布局还静态导入搜索和浮动聊天。这些功能应通过共享层的 `React.lazy` / `Suspense` 建立按需边界，减少任何工作区页面首次进入时必须加载和解析的代码。
- 收紧只为一个符号而导入大范围 `index.ts` 的路径；先沿真实构建依赖图处理，不全仓机械替换。
- 验收：比较坦克页和 Agent 页首批 JS、公共布局模块数量、首次交互延迟；同时验证首次打开弹窗和搜索的加载反馈。

### P1：关闭的浮动聊天停止重订阅与渲染

相关位置：`packages/views/chat/floating-chat.tsx`、`packages/views/chat/components/chat-window.tsx:99`。

- ChatWindow 在关闭状态仍挂载，通过透明度、inert 和 pointer-events 隐藏。agents、members、sessions、projects、消息分页和 pending-task 查询在组件顶部订阅，没有统一按 `isOpen` 禁用。
- 隐藏时仍会接收 Query 变化、合并消息分页，并保留编辑器和消息树。应把全局未读/任务状态与实际聊天内容拆开：保留轻量全局数据，内容查询与渲染按可见性启用。
- 使用已有 Query 缓存、草稿存储和滚动恢复保持重开体验；不能丢失草稿、未读状态或后台任务完成通知。
- 验收：关闭聊天后发送模拟实时事件，确认重组件不继续渲染，重开仍正确恢复。

### P1：合并聊天生命周期触发的刷新

相关位置：`packages/core/realtime/use-realtime-sync.ts:1626` 及聊天发送 mutation。

- queued、dispatch、running 和发送完成路径在很短时间内分别触发 pending-task 和消息刷新；日志已经观察到同接口的重复请求。
- 按会话与 query key 合并短窗口 invalidation，并处理进行中请求的 trailing refresh；可先实验 100–250ms 的合并窗口。
- 只对载荷足够完整的事件直接更新 Query 缓存；队列端点仍保留服务端权威性，不能据不完整事件推断完整队列。
- 验收：相同事件序列下请求次数下降，同时排队、取消、失败、完成及重连状态保持正确。

### P1：把同步持久化和日志移出输入热路径

相关位置：`packages/core/chat/store.ts:496`、`packages/core/platform/storage.ts`、`packages/core/logger.ts:24`。

- 每次输入调用 `setInputDraft`，复制草稿表，再由 `writeDrafts` 遍历并 JSON 序列化整个工作区草稿集合，同步写入 localStorage。
- logger 的 debug 仍直接输出到 console，没有等级过滤；当前开发日志里能看到逐次输入记录。
- 内存草稿即时更新，持久化短暂防抖，并在切换会话、发送、失焦与 pagehide 时保证 flush。可以进一步按会话拆分存储键，降低草稿总量增加后的写入成本。
- 日志阈值由宿主注入；默认关闭高频 debug，保留显式开启诊断的能力，遵守 core 不读取 process.env 的边界。
- 验收：中文输入法、大草稿、多会话、切换与刷新恢复；记录键入到绘制的延迟和存储写入次数。

### P2：游戏静止时停止无效绘制和 React 更新

相关位置：`packages/views/tank-defense/tank-battle.tsx:108`、`packages/views/siege/campaign/campaign-app.tsx`。

- 坦克运行循环在 ready、暂停与结束画面仍每帧 paint，并每 80ms 生成 snapshot 触发整页 React 更新。战役也有持续绘制与定时 HUD 更新。
- 把 Canvas 与配置/说明面板分离；无场景变化时停止绘制和 HUD 更新，仅在状态、尺寸或明确动画变化时重绘。运行时 HUD 优先更新真正变化的字段。
- 现有固定步长、最大追帧与隐藏页面暂停已有保护，应保留；这不是建议重写游戏物理系统。
- 验收：ready/暂停页面空闲 CPU、运行帧时、长任务、关卡与全屏退出行为。本次未获得有效 FPS 数据，优先级低于前述已测的页面加载问题。

### P2：核实 MDX 与 Turbopack 的兼容，再评估更换开发编译器

- `apps/web/next.config.ts:100` 记录了为 MDX 兼容保留 Webpack 的原因。应针对当前依赖建立小范围兼容性验证，再决定升级 MDX、隔离内容编译或切换编译器。
- 不把删除 `--webpack` 当作已验证修复，也不承诺固定加速倍数。
